# Persistence Architecture

This document is the source of truth for the current Spendly EF Core and
PostgreSQL persistence layer.

The implementation follows
[ADR 0003: Define domain model persistence strategy](../adr/0003-define-domain-model-persistence-strategy.md).

## Current status

Production persistence was completed in milestone:

```text
v0.4 Persistence Layer
```

The implemented layer includes:

- production `SpendlyDbContext`;
- production EF Core configurations;
- explicit converters and physical PostgreSQL names;
- the `InitialCreate` migration;
- DI registration through a shared `NpgsqlDataSource`;
- startup validation for the connection string;
- PostgreSQL readiness checking;
- migration, schema, materialization, and relationship tests against a real
  PostgreSQL Testcontainer;
- CI validation for pending EF Core model changes.

Application persistence ports and repositories are intentionally absent until
real use cases define their contracts.

## Dependency registration

`Spendly.Infrastructure.DependencyInjection.AddInfrastructure` registers:

1. `PostgreSqlOptions` with startup validation;
2. one singleton `NpgsqlDataSource`;
3. scoped `SpendlyDbContext` instances using that data source;
4. the PostgreSQL readiness health check.

The shared data source owns connection pooling. A `DbContext` is still scoped
and must not be reused concurrently or promoted to a singleton.

The migrations assembly is explicitly set to the Infrastructure assembly.

## Physical schema

The initial migration creates three application tables.

### wallets

| Column | PostgreSQL type | Null | Notes |
| --- | --- | --- | --- |
| `id` | `uuid` | no | Primary key; generated by Domain |
| `name` | `character varying(100)` | no | Normalized wallet name |
| `type` | `smallint` | no | Checked `WalletType` code |
| `currency_code` | `character varying(3)` | no | Checked uppercase code |
| `created_at` | `timestamp with time zone` | no | UTC instant |

Constraints:

```text
pk_wallets
ck_wallets_type_defined
ck_wallets_currency_code_format
```

### categories

| Column | PostgreSQL type | Null | Notes |
| --- | --- | --- | --- |
| `id` | `uuid` | no | Primary key; generated by Domain |
| `name` | `character varying(100)` | no | Normalized category name |
| `type` | `smallint` | no | Checked `CategoryType` code |
| `created_at` | `timestamp with time zone` | no | UTC instant |

Constraints:

```text
pk_categories
ck_categories_type_defined
```

### transactions

| Column | PostgreSQL type | Null | Notes |
| --- | --- | --- | --- |
| `id` | `uuid` | no | Primary key; generated by Domain |
| `type` | `smallint` | no | Checked `TransactionType` code |
| `wallet_id` | `uuid` | no | Required wallet foreign key |
| `category_id` | `uuid` | no | Required category foreign key |
| `occurred_at` | `timestamp with time zone` | no | UTC instant |
| `description` | `character varying(500)` | yes | Normalized optional text |
| `created_at` | `timestamp with time zone` | no | UTC instant |
| `updated_at` | `timestamp with time zone` | yes | `NULL` until updated |
| `amount` | `numeric(19,4)` | no | Positive exact decimal |
| `currency_code` | `character varying(3)` | no | Currency of `Money` |

Constraints and indexes:

```text
pk_transactions
fk_transactions_wallets_wallet_id
fk_transactions_categories_category_id
ck_transactions_type_defined
ck_transactions_amount_positive
ck_transactions_currency_code_format
ix_transactions_wallet_id
ix_transactions_category_id
ix_transactions_occurred_at
```

Both foreign keys use `ON DELETE RESTRICT`. A wallet or category referenced by
financial history cannot be deleted accidentally through a cascade.

## Strongly typed identifiers

Domain identifiers are type-safe wrappers:

```text
WalletId
CategoryId
TransactionId
```

Each wraps `Guid` and new identifiers are generated through UUID version 7.
Persistence uses explicit `ValueConverter<TId, Guid>` implementations.

The storage chain is:

```text
strongly typed ID -> Guid -> PostgreSQL uuid
```

Every identifier property uses `ValueGeneratedNever()`. PostgreSQL does not
generate, replace, or reinterpret identifiers created by the Domain.

No custom `ValueComparer` is required because the identifiers are immutable
`readonly record struct` values with correct value equality.

## Currency storage

`Currency` is a Domain value object. It is stored as its normalized code:

```text
Currency -> string -> character varying(3)
```

Examples:

```text
Currency.Rub -> RUB
Currency.Usd -> USD
Currency.Eur -> EUR
```

The code is required and constrained by the PostgreSQL expression:

```sql
currency_code ~ '^[A-Z]{3}$'
```

`Currency` is not serialized as JSON and does not require a separate lookup
table. The current Domain validates format, not membership in a complete ISO
4217 registry.

## Money storage

`Money` is mapped as a required EF Core complex property. It is flattened into
the containing table:

```text
Money.Amount   -> amount
Money.Currency -> currency_code
```

For example, `1500.2500 RUB` is stored as:

```text
amount = 1500.2500
currency_code = RUB
```

Money is not stored as JSON, a composite PostgreSQL value, or a serialized
string. Amount and currency remain independently queryable and constrained.

### Precision and scale

All monetary columns use:

```text
numeric(19,4)
```

The policy is shared with the Domain constants:

```text
precision: 19
scale: 4
maximum: 999999999999999.9999
```

A `decimal` value is used throughout the Domain and persistence path. Monetary
values must not be converted through `float` or `double`.

Transactions additionally use `amount > 0`, matching the current Domain rule
that every recorded income or expense amount is positive.

## Enum storage

Persisted enums are converted to `short` and stored as PostgreSQL `smallint`:

```text
WalletType
CategoryType
TransactionType
```

The database stores numeric codes rather than CLR names. Check constraints
allow only currently defined codes.

Existing numeric values are part of the database contract:

- do not change or reuse an existing numeric value;
- assign a new numeric value to a new member;
- a member rename must keep its numeric value;
- update the check constraint through a migration when adding a supported code.

## Date and time storage

Domain instants use `DateTimeOffset` and are normalized to UTC before
persistence.

PostgreSQL stores them as:

```text
timestamp with time zone
```

This represents an absolute instant. PostgreSQL does not preserve the original
client offset or an IANA time-zone identifier.

Required values:

- `Wallet.CreatedAt`;
- `Category.CreatedAt`;
- `Transaction.OccurredAt`;
- `Transaction.CreatedAt`.

Nullable value:

- `Transaction.UpdatedAt`.

`NULL` means that the transaction has not been updated since creation.

## Domain and database invariant boundaries

The Domain remains the primary owner of business invariants. PostgreSQL repeats
cheap structural checks that protect data written outside normal application
paths.

The rule that transaction currency equals wallet currency remains in Domain
logic. A row check cannot compare a transaction column with a referenced wallet
row. A trigger or denormalized compound key would require a separate decision.

## Why repositories are absent

The database layer is implemented, but Application use cases are not.

Repository interfaces are not created per table. A persistence port appears
only when a concrete use case defines a required operation and ownership of the
contract.

Examples of future focused ports may include:

```text
save a newly created wallet
load transactions for a wallet and period
check whether a category exists and is active
```

A generic CRUD repository is not used because it:

- duplicates much of `DbSet<TEntity>`;
- hides use-case intent behind `GetAll`, `Add`, and `Update`;
- encourages the same access model for entities with different rules;
- makes query shape and transaction boundaries less explicit;
- becomes an abstraction over EF Core rather than an Application contract.

Application will define the smallest domain-specific port, and Infrastructure
will implement it with EF Core.

## Connection-string configuration

The API reads:

```text
ConnectionStrings:SpendlyDatabase
```

`PostgreSqlOptionsValidator` requires:

- a non-empty, valid PostgreSQL connection string;
- `Host`;
- `Database`;
- `Username`.

The password is not required by the validator because some environments may use
another authentication mechanism. The selected environment is responsible for
providing every credential required by its PostgreSQL server.

### User Secrets

From `backend`:

```bash
dotnet user-secrets set "ConnectionStrings:SpendlyDatabase" "Host=localhost;Port=5432;Database=spendly;Username=spendly;Password=spendly_password" --project src/Spendly.Api/Spendly.Api.csproj
```

### Environment variable

```text
ConnectionStrings__SpendlyDatabase
```

PowerShell:

```powershell
$env:ConnectionStrings__SpendlyDatabase = "Host=localhost;Port=5432;Database=spendly;Username=spendly;Password=spendly_password"
```

Bash:


## Migration workflow

Run the following commands from `backend`.

### Create

```bash
dotnet ef migrations add MigrationName --project src/Spendly.Infrastructure/Spendly.Infrastructure.csproj --startup-project src/Spendly.Api/Spendly.Api.csproj --context SpendlyDbContext --output-dir Persistence/Migrations
```

Review the migration and model snapshot. Migration files are committed with the
model change that requires them.

### Verify the model snapshot

```bash
dotnet ef migrations has-pending-model-changes --project src/Spendly.Infrastructure/Spendly.Infrastructure.csproj --startup-project src/Spendly.Api/Spendly.Api.csproj --context SpendlyDbContext
```

CI runs this check after the Release build. A failure means the current EF Core
model differs from the committed migration snapshot.

### Apply

```bash
dotnet ef database update --project src/Spendly.Infrastructure/Spendly.Infrastructure.csproj --startup-project src/Spendly.Api/Spendly.Api.csproj --context SpendlyDbContext --connection "Host=localhost;Port=5432;Database=spendly;Username=spendly;Password=spendly_password"
```

### Roll back to a target migration

```bash
dotnet ef database update PreviousMigrationName --project src/Spendly.Infrastructure/Spendly.Infrastructure.csproj --startup-project src/Spendly.Api/Spendly.Api.csproj --context SpendlyDbContext --connection "Host=localhost;Port=5432;Database=spendly;Username=spendly;Password=spendly_password"
```

Target `0` only for a database where removing every application migration is
intended.

### Remove the latest unshared migration

```bash
dotnet ef migrations remove --project src/Spendly.Infrastructure/Spendly.Infrastructure.csproj --startup-project src/Spendly.Api/Spendly.Api.csproj --context SpendlyDbContext
```

Only remove a migration that has not been shared or deployed. Correct an
already shared migration with a new migration.

## Why migrations are not applied at API startup

Neither API nor Worker calls `Database.Migrate()` or `Database.MigrateAsync()`.

Schema deployment is explicit because:

- concurrent application replicas must not race for DDL changes;
- migration review and rollout order belong to deployment;
- runtime identities should use only the permissions they need;
- destructive or data-rewriting changes require a data plan;
- restarts and readiness checks must not mutate schema state.

A deployment can apply a reviewed SQL script, an EF Core migration bundle, or a
controlled `dotnet ef database update` step. The chosen mechanism must run once
for the target environment before the new application version serves traffic.

## Readiness

Default endpoints:

```text
GET /health/live
GET /health/ready
```

Liveness executes no dependency checks.

Readiness executes the application self-check and the `postgresql` check. The
PostgreSQL check:

- opens an Npgsql connection;
- executes `SELECT 1`;
- uses a five-second timeout;
- returns a safe healthy or unhealthy description;
- does not create the database schema;
- does not apply migrations;
- does not expose provider errors or secrets.

A successful readiness response proves connectivity, not that a pending
migration is absent. Migration state is verified by CI and deployment checks.

## Database integration tests

Default tests do not require Docker:

```bash
cd backend
dotnet test Spendly.sln
```

They include EF Core metadata tests that inspect the production model without
opening a connection.

Run explicit PostgreSQL tests:

```bash
dotnet test tests/Spendly.IntegrationTests/Spendly.IntegrationTests.csproj --settings tests/docker.runsettings
```

The database suite uses:

- production `SpendlyDbContext`;
- production migrations;
- Npgsql;
- PostgreSQL `17.10` through Testcontainers;
- a new context for materialization checks;
- schema reset between shared-fixture tests.

It verifies:

- complete migration application to an empty database;
- ordered known and applied migrations;
- no pending migrations after application;
- the physical table, column, constraint, foreign-key, and index shape;
- wallet, category, and transaction write/read round trips;
- strongly typed ID, Currency, Money, enum, and timestamp materialization;
- restrictive delete behavior;
- rollback and successful migration reapplication;
- queryability of every production `DbSet`;
- readiness behavior without schema mutation.

The migration smoke test uses a dedicated empty container and never relies on
`EnsureCreated()`.

## Secrets that must not be committed

Do not commit:

- real database passwords;
- complete production or shared-environment connection strings;
- `deploy/.env` and other environment-specific secret files;
- cloud access keys, API tokens, CI tokens, or secret-manager credentials;
- private keys, signing keys, client certificates, or certificate passwords;
- database backups or logs containing personal or production data.

Safe tracked content includes configuration key names, redacted examples,
`.env.example`, and isolated local or ephemeral Testcontainers defaults.
